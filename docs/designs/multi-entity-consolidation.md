## Problem Statement

A prior competitive-research pass verified that Rillet's one genuine advantage
over Rekono is native multi-entity financial consolidation -- combining
multiple legal entities' books into one set of statements with intercompany
eliminations. Rekono has no equivalent today: one entity per organization,
full stop. The user asked to scope out closing this gap.

## Demand Evidence

None, directly. Rekono is pre-launch -- no live users, no paying customers.
The only evidence for this feature is market-level: Rillet's own marketing
centers multi-entity consolidation as a core differentiator, which proves the
segment Rillet targets cares enough to pay for it. That is evidence about
Rillet's market, not evidence that a Rekono prospect has hit this wall. No
one has been asked directly.

## Status Quo

Not verified against real prospects. General market research (not
Rekono-specific) shows three common patterns for companies that need this and
don't have it: manual consolidation in Excel (combine each entity's trial
balance by hand, eliminate intercompany transactions manually, every close);
running separate instances of the same tool per entity with no real
consolidation; or bolting a dedicated consolidation product (Sage Intacct,
NetSuite, OneStream) on top of otherwise-unconnected books. Which of these
Rekono's actual prospects live with is unknown.

## Target User & Narrowest Wedge

No named person. Asked directly for a specific role/company/consequence, the
answer was "we hope to have large scale companies using our software" --
a company-size aspiration, not a person. This was flagged directly during
the session as not meeting the bar: a category is not a customer.

Narrowest wedge, if this is ever built: **a fake-door test, not code.** See
The Assignment below.

## Constraints

- Pre-launch product, zero real users -- nothing here can lean on observed
  behavior, only inferred market patterns.
- Must respect Rekono's existing ledger conventions: `postJournalEntry` as
  the sole write path, immutable posted entries (corrections via reversing
  entries), integer-cents throughout, and RLS tenant isolation enforced at
  the `orgId` level across 65 tables (`RLS_TABLES.length` in
  `backend/src/rls.js`, verified against the running code, not estimated).
- Whatever ships first must not put the existing single-entity product at
  risk -- Rekono's real, validated advantages (pricing transparency,
  same-day trial-balance import, cap table depth) are what's actually
  competing right now.

## Premises

   deadline, and no trigger condition, which the second opinion correctly

## Approaches Considered

### Approach A: Cross-org consolidation report (QuickBooks/Xero pattern)

**Scoped for when triggered -- not a green light.** The concreteness below
is so the plan is ready to execute the day the fake-door test succeeds, not
a signal that this should start now.

Each subsidiary stays a normal, separate Rekono organization. Zero changes
to `journal_entries`, `accounts`, `invoices`, or any of the 65 existing
RLS-scoped tables; `postJournalEntry`, every financial-statement function,
and the RLS policy set are untouched. New surface, minimal:

- `OrganizationGroup` (`id`, `name`, `createdByUserId`) and a join table
  `OrganizationGroupMember` (`groupId`, `orgId`, `addedByUserId`,
  `addedAt`) -- both new tables, both need registering in `rls.js`'s
  `DIRECT_ORG_TABLES`/`DERIVED_TABLES` per CLAUDE.md's own "Adding a
  feature" checklist, since they carry `orgId`-adjacent data even though
  they're consolidation-only.
- A "consolidation viewer" permission: a user can only run the report for a
  group if they hold this permission on every member org.
- **The hard part the report has to solve, stated plainly rather than
  glossed over:** this codebase's RLS enforces exactly one `orgId` per
  transaction via `SET LOCAL rekono.org_id` (`rls.js`), and the "system
  context" escape hatch is reserved for boot-time/pre-auth flows, not
  authenticated user-triggered reads. A cross-org report therefore cannot
  be one query -- it has to call each existing financial-statement function
  once per member org, each inside its own `runWithOrgContext(orgId, fn)`
  transaction, and combine the N results in application code afterward.
  This is a real (if mechanical) change to how those functions get called,
  not a untouched-everything claim -- correcting the earlier draft, which
  understated this.
- **Account-matching rule for combining trial balances (open design
  question, not solved here):** each org's chart of accounts is seeded
  independently, so there's no guarantee "Accounts Payable" in org A and
  org B share an ID, or even a name. The report needs either a match-by
  `(name, type)` heuristic (fragile -- a renamed account breaks it
  silently) or an explicit one-time mapping step in the consolidation UI
  where a human maps each member org's accounts to a shared consolidated
  chart. The mapping-step version is safer and is the one to build --
  named here so it doesn't get discovered mid-implementation.
- **Intercompany eliminations are report-only, never posted.** A declared
  elimination is a row in a new `ConsolidationAdjustment` table
  (`groupId`, `description`, `accountMatch`, `amountCents`,
  `createdByUserId`) that exists solely to net out of the *report's*
  numbers -- it is never a `JournalEntry` and never touches any member
  org's real, standalone books. Also needs RLS registration (derived off
  `OrganizationGroup`).

Completeness: 6/10 (no true intercompany auto-matching or account
auto-mapping; a controller declares both). Effort, broken down rather than
asserted: 2 new models + RLS registration + tests (~2-3 days), the
per-org-loop report function reusing existing statement functions
(~2-3 days), the consolidation-viewer permission check (~1 day). The
mapping-step UI is the least certain estimate -- a naive one-to-one
account mapper is ~2-3 days, but the outside voice correctly flagged that
real independently-seeded charts of accounts have subtotals, hierarchies,
and mismatched sub-types, which can turn "map account A to account B"
into a genuine small data-integration problem rather than a form; budget
~3-5 days and treat it as the item most likely to slip. Total: human
~2-2.5 weeks, not the flatter ~1.5-2 originally stated; several focused
AI-assisted sessions given the new-model test gate in CLAUDE.md.

### Approach B: Entity dimension inside one org (Sage Intacct pattern)

Add an `Entity` model nested under `Organization`. Most of the 65
RLS-scoped tables -- every ledger, invoice, vendor, and bank table
(`journal_entries`, `accounts`, `invoices`, `vendors`, `bank_accounts`, and
similar; excluding org-administrative tables like `users` and
`audit_logs`, which stay org-level) -- gets an `entityId` column.
`postJournalEntry` enforces balance per-entity, not just
per-org. A new consolidation module sums across entities and auto-applies
elimination rules for accounts flagged as intercompany. This does not cross
the existing RLS security boundary -- organization stays the enforced
tenant, entity is an application-level dimension inside it -- but it touches
most of the ledger's read and write paths.

Completeness: 10/10 (matches how real GL-native consolidation works,
including automatic intercompany matching). Effort: human 6-10 weeks;
several AI-assisted sessions, given CLAUDE.md's own gate that every touched
module needs tests asserting against the trial balance, not just its own
endpoint.

## Recommended Approach

Approach A, and only after the fake-door test in The Assignment produces a
real signal (see the corrected threshold there).

**Caveat surfaced by the outside voice, not resolved here:** the fake-door
test validates that someone wants *some* multi-entity capability. It does
not validate that Approach A's report-only eliminations -- never posted,
never reconciled to any member org's real ledger -- meet the bar for a
finance team trying to replace an auditable Excel-based close. That is an
unverified assumption baked into the steelman, not a solved detail. If the
test succeeds, confirming this with the actual respondent is the required
next step before writing Approach A's code (see The Assignment).

**Correction on sequencing:** Approach B is not "next" after Approach A in
any technical sense -- their data models share almost nothing (A: an
org-group linking table and report-only adjustments; B: an `entityId`
column threaded through most of the ledger). Building A first buys no
architectural head start toward B and would be fully throwaway work if B
is ever needed. The two are independent bets, not stages of one plan. A is
recommended first only because it is far cheaper to be wrong about.

## Architecture Decisions (from eng review)

- **Permission model:** each member org's own admin explicitly grants
  "consolidation viewer" to specific users. An org's books are never
  exposed to the rest of the group without that org's own admin opting in
  per-user -- no group-owner-grants-all shortcut. Matches Rekono's
  existing per-org admin model; no new global role concept needed.
- **Partial-failure behavior:** if any member org's statement query fails
  during the per-org loop, the report fails entirely and names the
  specific org and error -- it never shows a consolidated total with one
  entity silently missing. A financial statement that's wrong by omission
  is worse than no statement.

## Open Questions

- Whether "consolidation viewer" access needs a real RLS policy (a third
  GUC alongside the org/system context split) or an application-layer
  membership check ahead of the per-org loop is sufficient given the
  report is read-only and already calls `runWithOrgContext` per org one at
  a time. Leaning application-layer, but worth a second look against
  `rls.js`'s existing system-context comments when this is actually built.
- Currency translation (foreign subsidiaries) is out of scope for both
  approaches as scoped -- neither addresses multi-currency consolidation.
  If a validated prospect needs that, it changes Approach A's shape.

## Performance Note (from eng review)

Approach A's per-org loop runs one `runWithOrgContext` transaction per
member org, sequentially. For the realistic scale this is scoped for (2-5
entities), this is a non-issue -- flagging only so it isn't silently
assumed to scale to a group with hundreds of member orgs, which it
wouldn't without batching.
